## Intent

**Problem:** The tablet sits in a rental office and holds every rupiah the owner has taken. FR-17
asks for a screen lock so that someone who picks it up does not read the books — and the PRD is
equally insistent about what that lock is **not**: *"Kunci layar adalah penghalang, bukan keamanan
sungguhan. Tidak ada bedanya antara aplikasi terkunci dan terbuka bagi orang yang memegang
tablet."* Both halves are requirements. A lock that oversells itself is a lock the owner trusts
with more than it can carry.

There is also a way out to build, and it is the part that decides whether the feature is safe to
turn on at all: a recovery code, shown once, that lets the owner back in when the PIN is forgotten.
Without it, the first forgotten PIN costs the data the whole epic exists to protect.

**Approach:** PBKDF2-hashed 4-digit PIN and a 20-character recovery code, both in the existing
`settings` table. A full-screen lock above the shell. Auto-lock driven by an **absolute
timestamp** persisted at background entry. Five failed attempts lock input with a visible
countdown.

## Boundaries & Constraints

**Always:**
- **The copy says the lock is a barrier, and says nothing more.** FR-17 forbids reusing the
  prototype's *"Data tersimpan lokal & terenkripsi di perangkat ini"* — the prototype's own lock
  screen carries that sentence (`prototype/index.html:58`) and it is false: the database is a
  plain SQLite file. Every string this story adds states the barrier and stops.
- **The PIN is stored as PBKDF2WithHmacSHA1 + a random per-setting salt**, never in a readable
  form, and never in a log, an export, or an error message (NFR-5).
- **The recovery code is alphanumeric, at least 20 characters, generated by `SecureRandom`, shown
  exactly once**, and hashed like the PIN. It is not 4–6 digits: the PRD's own note says that
  would be a PIN with an extra step.
- **The flow is not finished until the owner confirms they wrote the code down.** The AC is
  explicit, and it is the difference between a recovery code that exists and one that was
  dismissed.
- **Auto-lock is computed from a persisted absolute timestamp**, not a counter. A counter resets
  on process death, which is exactly the case the AC names.
- **Five consecutive failures lock input with a visible countdown.** The count and the lockout
  deadline are **persisted**, so force-quitting the app does not clear them.
- **The lock covers the whole app**, including the shell's search bar — a lock that leaves a
  search field reachable is not a lock.
- **Every key this story writes is added to `BackupJson.NEVER_EXPORTED`.** See the decision below;
  this is the one that can destroy the app.
- **The recovery code replaces the PIN, and the old code stops working** — a new code is issued
  with the new PIN, because a code that survives its own use is a permanent second key.

**Never:**
- **No biometrics.** The prototype's settings screen has a "Biometrik" switch; nothing in FR-17
  asks for it, it needs a dependency, and it would be a second unlock path to keep in step with
  the first.
- **No encryption of the database.** Not asked for, and claiming it is what FR-17 forbids.
- **No PIN change without the current PIN or the recovery code.** A "change PIN" that only needs
  the app open is a lock the holder can walk through.
- **No recovery-code display after the one showing.** Not in settings, not in a "show me again"
  dialog. The hash cannot be reversed, and storing the plaintext to re-show it would put it back
  in the database the lock is protecting.
- **No lock on the export.** A backup file is not encrypted and the lock is not a security
  boundary; pretending otherwise would make the export look safer than it is.
- **No shake on anything but a genuinely wrong PIN** — once per failure, never on a correct entry,
  never looping.

## Decisions taken at the gate

- **`NEVER_EXPORTED` must list every PIN key, not just the two hashes.** This is the decision that
  can destroy the app, and it is worth stating in full. Story 5.1 shipped
  `setOf("pinHash", "recoveryHash")` as a placeholder for this story. But 5.3 also writes
  `pinEnabled`, `pinSalt`, `recoverySalt`, `pinAttempts`, `pinLockoutUntil` and
  `autoLockMinutes`. With only the hashes excluded, a backup taken while the PIN was on would
  restore `pinEnabled=true` and **no hash** — a device whose lock can never be opened, holding the
  owner's data, on the day they restored it because they had lost a device. The list becomes every
  key the story writes, and the existing tests' fixture grows a `pinEnabled` row so the exclusion
  is proven rather than assumed.
- **The recovery code is hashed with the same PBKDF2, at the same iteration count.** A cheaper hash
  for a higher-entropy secret would be defensible arithmetic and a bad rule: two hash strengths in
  one file is two things to keep in step, and the code's 119 bits do not need the discount.
- **Iterations are a constructor parameter with the production value as the default.** Tests pass a
  low count so a suite of twenty PIN tests does not spend a minute hashing, and one test asserts
  the **default** is at least the documented floor. A test-only constant baked into the class would
  make every test slow; a low default with tests asserting nothing would ship a weak hash.
- **The shake builds its own `tween`, and `KnMotion.tween` is not widened.** `Motion.kt` rejects
  any duration outside 140/220/300, and that guard is what keeps a stray `tween(500)` out of the
  codebase. The UX doc carves out exactly one 420ms exception by name, so the token is added as
  `KnMotion.shakeMillis` and the lock screen calls `tween(KnMotion.shakeMillis)` directly. Widening
  `tween`'s allowed set would make 420ms available everywhere for a rule that names one place.
- **The lock screen replaces the shell rather than covering it.** `if (locked) LockScreen(...) else
  AppShell(...)`, not a `Box` with an overlay. An overlay draws the destination underneath it — a
  screenshot, a screen reader, or a rendering bug would expose the books behind a lock. Not
  composing the shell at all is the only version where "locked" means the content is not on screen.
- **The cold-start rule is "always lock", and the timestamp governs the warm path.** The AC asks
  for both *"dihitung dari timestamp absolut"* and *"proses mati atau restart → terkunci lagi"*.
  A single timestamp check cannot do the first clause on a cold start where `onStop` never ran
  (process killed in the foreground), so: the **first** `onStart` of a process locks
  unconditionally when the PIN is on, and every later `onStart` compares against the persisted
  timestamp. Both clauses hold, and the safer behaviour is the one that applies when the app cannot
  know what happened.

## Design Notes

**The lock is a barrier and the copy has to mean it.** FR-17 spends more words on what the lock is
*not* than on what it is, and the reason is concrete: the prototype's lock screen says *"Data
tersimpan lokal & terenkripsi di perangkat ini"* (`prototype/index.html:58`), the database is a
plain SQLite file, and an owner who believes the first sentence will hand the tablet to a customer
with more confidence than the truth allows. Every string here says "PIN" and "kunci" and stops.
The same rule is why the export is not locked: a backup file is not encrypted either, and a lock
on the button would imply the file is.

**`NEVER_EXPORTED` was a placeholder that this story has to fill, and filling it wrongly bricks
the app.** Story 5.1 shipped two keys so the exclusion mechanism would exist before the rows did.
This story adds six more keys, and the failure mode of leaving any of them out is not a leaked
hash — it is `pinEnabled=true` restored onto a device with no hash, which is a lock nobody can
open, on the day the owner restored a backup because they had lost their phone. The list grows to
every key, the existing backup test grows a `pinEnabled` row, and the exclusion is asserted per key
rather than for "the hashes".

**A counter is not a timestamp, and the AC says so twice.** *"Dihitung dari timestamp absolut saat
masuk background, bukan counter yang reset"* — the counter would be the obvious implementation and
it resets on exactly the event the AC names. The timestamp is persisted in `settings`, which means
it survives process death for the same reason the cutoff day does.

**The cold-start clause cannot be satisfied by the timestamp alone, and the honest answer is to
lock.** If the process is killed in the foreground, `onStop` never ran and there is no timestamp to
compare — so a pure timestamp check would leave a freshly-restarted app unlocked. The AC also says
*"proses mati atau restart → terkunci lagi"*. Locking on the first `onStart` of a process satisfies
both clauses, and it fails safe: the case where the app cannot know what happened is the case where
it locks.

**A 420ms animation is a named exception, not a widened rule.** `KnMotion.tween` refuses anything
outside 140/220/300 and that guard is worth keeping — it is what stops a `tween(500)` appearing on
some future screen. The UX doc carves out the PIN shake by name and duration. So the token is
`KnMotion.shakeMillis` and the one call site passes it directly; `tween`'s allowed set stays closed.
